# מערכות עיצוב

כל מערכת עיצוב חדשה מנוהלת כקובץ `DESIGN.md` לפי הפורמט של `@google/design.md`. הקובץ משלב טוקנים מדויקים ב־YAML עם הסבר אנושי על אופן השימוש בהם.

## מבנה

```text
docs/design-systems/
  <design-system-id>/
    DESIGN.md
```

יוצרים מערכת עיצוב לפי קהל או משפחת עמודים, לא לפי עמוד יחיד. כמה עמודים יכולים להשתמש באותה מערכת כאשר הם פונים לאותו קהל, עוסקים באותה בעיית ליבה ומשתמשים באותה שפה חזותית.

## מקור אמת

- `DESIGN.md` הוא מקור האמת לעיצוב הפעיל של המשפחה.
- קובץ הקהל מגדיר למי פונים ולמה; `DESIGN.md` מתרגם זאת לצבע, טיפוגרפיה, ריווח, צורה ורכיבים.
- קוד CSS ורכיבי ממשק מממשים את `DESIGN.md` ואינם מחליפים אותו.
- רשומות תחת `docs/decisions/design/` מסבירות למה התקבלה החלטה, אך אינן מחזיקות את הערכים הפעילים.
- כל `DESIGN.md` חייב להיות שלם ועצמאי. אין להניח ירושה או import בין מערכות עיצוב.

## יצירה ועדכון

1. מתחילים מ־`docs/templates/DESIGN.md` ומעתיקים אותו ל־`docs/design-systems/<design-system-id>/DESIGN.md`.
2. קוראים את מקורות האמת של הקהל והמוצר לפני קביעת הטוקנים.
3. מחליפים את כל ערכי הדוגמה ומסירים סעיפים שאינם חלים. סעיף שהושמט בכוונה מתועד בשדה `omitted` לפי המפרט.
4. מריצים `npm run design:check` ומתקנים שגיאות ואזהרות רלוונטיות.
5. מתעדים שינוי מהותי ברשומת החלטה ומעדכנים את המימוש רק לאחר שהקובץ עבר בדיקה.

## תקופת המעבר

`reading-foundations.md` מתעד את המצב שיושם בעבר, אך אינו קובץ `DESIGN.md` מאושר ואינו בסיס להעתקה. הוא יישאר זמנית כדי לא לאבד את מצב המערכת הקיימת, עד שיושלם תהליך העיצוב מחדש וייווצר `reading-foundations/DESIGN.md`. באותו שינוי מוחקים את הקובץ הישן.

הבדיקה האוטומטית מאפשרת מצב שבו עדיין אין קובצי `DESIGN.md`, אבל מרגע שנוסף קובץ היא בודקת אותו באמצעות ה־linter הרשמי.
